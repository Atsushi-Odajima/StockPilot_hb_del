# INVENTORY_RULES — 在庫業務ルール（実装と一致させること）

実装の主な場所：`src/server/services/inventory.ts`（台帳エンジン）、`po.ts`、`stocktake.ts`、`replenish.ts`、`src/domain/*.ts`。

## 1. 数量の定義

| 用語 | 定義 | 実装 |
|---|---|---|
| 現物在庫 | その場所に記録されている数量（通常＋保留） | `balances.qty` |
| 利用可能在庫 U | **通常**場所の現物在庫合計。負数にならない | `kind='normal'` の合計 |
| 保留在庫 | **保留**場所の現物在庫合計。出庫・補充計算に含めない | `kind='hold'` の合計 |
| 発注残 O | 発注済み（`status='placed'`）明細の Q−R−C の合計。補充では**通常場所へ入る**明細だけ | `po_lines` |
| 補充判断数量 P | U＋O。「現在庫」とは呼ばない | `computeReplenishment` |

- 台帳キー＝ワークスペース（事業者のデータ世代）×SKU×場所。商品グループは表示用で在庫を持たない。
- 発注残を現物在庫や出庫可能数に加算しない。予約・引当・出庫予定はない。下書きは在庫を予約しない。
- 単位はSKUごとの整数（個・枚・本…）。異なる単位を合算した「在庫総数」は表示しない（SKU数と単位付き数量を表示）。

## 2. 台帳（ledger_events）

- 在庫の変動は追記のみのイベント。UPDATE は DB トリガーで常に拒否、DELETE はワークスペース削除（アカウント削除・サンプル再作成・退避世代の破棄）の連鎖時のみ許可。
- `balances` は同一トランザクションで更新する集計キャッシュ。`GET /api/verify` と `verifyLedger()` で台帳合計と照合できる。復元時も照合する。
- イベント種別：初期在庫 / 発注入荷 / 発注外入庫 / 販売目的出庫 / その他出庫 / 顧客返品入庫 / 仕入先返品出庫 / 場所移動（出・入） / 破損・廃棄 / 棚卸調整 / 理由付き数量訂正 / 誤登録の取消。
- 各イベント：固定ID、確定順 `seq`、伝票ID、SKU、場所、符号付き数量、種別、業務日付、確定時刻、操作主体、関連（発注明細・元イベント・取消元・移動の相手行・棚卸）、理由、SKU名称・場所名のスナップショット。
- 業務日付（YYYY-MM-DD、Asia/Tokyo）と確定時刻を分ける。履歴の順番は確定順（`seq`）。過去日入力で系列を並べ替えない。
- 入出庫数量は正の整数を入力し、符号はサーバーが処理種別から決める。

## 3. 上限と入力検証

| 項目 | 値 | 守る場所 |
|---|---|---|
| 1明細の数量 | 1〜1,000,000 | zod スキーマ、`isValidOpQty` |
| SKU×場所の残高 | 0〜1,000,000,000 | サーバー（`BALANCE_LIMIT`）＋ DB CHECK |
| 1伝票の明細 | 200行（移動は往復で400イベント） | `MAX_LINES_PER_OP` |
| CSV | マスター5,000行・数量2,000行・5MB | `csv.ts` |

NaN・Infinity・小数・負数・桁あふれは拒否。負在庫は画面・サーバー・DB（CHECK qty>=0）の三重で防ぐ。

## 4. 確定処理（共通）

`applyOperation()` がすべての在庫変動（画面・スマホ・CSV・棚卸・発注入荷・取消）を処理する。
1. `tenants` 行を FOR SHARE → データ世代（dataEpoch）と利用権を検証
2. `command_log` に冪等キーを登録（同キー同内容＝前回結果、同キー別内容＝`IDEMPOTENCY_CONFLICT`）
3. 元伝票 → 発注明細 → 場所（ID順）→ 残高（SKU,場所順）の順にロック。存在しない残高行は0で作ってからロック（場所行ロックにより二重作成を防ぐ）
4. 棚卸停止・アーカイブ・画面表示時の数量（`expected`→`STALE_QTY`）・発注残・上限を再検査
5. 伝票番号の採番（`workspaces` 行のロックは常に最後）→ 伝票・台帳・残高・場所リビジョン・発注受領数を更新 → コミット後に応答
6. デッドロック・直列化失敗は同内容で最大3回再試行

不足時は `INSUFFICIENT_STOCK` で現数・必要数・他の場所の数量を返す。他の場所から自動で減らさない。

## 5. 取消・返品

| 操作 | 意味 | 数量の上限 |
|---|---|---|
| 誤登録の取消 | 入力ミスを反対方向の補償イベントで打ち消す。元と補償の両方が台帳に残る | 残り＝｜元数量｜−取消済み−（出庫／受領なら）返品済み |
| 顧客返品 | 実際に戻った商品。元の出庫行に関連付け、**保留場所**へ入庫 | 元の出庫の残り（上と同じ式） |
| 元履歴なし返品 | 履歴にない過去出荷の返品。理由必須、`no_source=true` | — |
| 仕入先返品 | 実際に仕入先へ返送。元の受領行を選び、返す場所から減らす。**発注の R・発注残は変えない**。追加発注は自動作成しない | 元の受領の残り |

- 取消の履歴・棚卸調整は取り消せない（正しい操作を登録し直す／再棚卸・理由付き訂正）。
- 移動の取消は相手側も同時に戻す（同じ数量）。発注入荷の取消は R も同じトランザクションで戻す。
- 取消で残高が負になる場合は拒否し、実態確認を促す。同じ取消の再送は冪等キーで1回だけ。別キーでも上限で拒否。
- 元伝票ヘッダー行を FOR UPDATE して、同じ元への取消・返品を直列化する。

## 6. 発注

- Q＝発注数量、R＝有効な実入荷累計（入荷イベント＋その取消の合計）、C＝未入荷打切り、O＝Q−R−C。常に 0≦R, 0≦C, R+C≦Q（DB CHECK）。
- 下書きは発注残に含めない。「発注済みにする」は利用者が実際に発注したことの記録。PDF作成・共有では状態を変えない。
- 発注済みの訂正は版と理由を残す（`po_revisions`）。既存明細は削除不可、数量は R+C 以上、入荷済み明細の場所は変更不可、SKUは変更不可。
- 状態（明細数量から導出）：下書き／発注済み（R=0,O>0）／一部入荷（R>0,O>0）／入荷完了（O=0,C=0）／残数打切り完了（O=0,C>0,R>0）／取消（R=0,C=Q）。
- 入荷：1回で複数明細・複数場所へ振り分け可。合計が O を超えると `OVER_RECEIPT`（在庫・発注ともに不変）。不足分は「未入荷として残す」か「理由付きで打ち切る」を選ぶ。保留へ入れた分も R に数える。保留→通常は移動（再入庫しない）。
- 交換用発注は新しい発注を作り `replaces_po_id` で関連付ける。

## 7. 補充

設定：0 ≦ 安全在庫 ≦ 発注点 ＜ 目標在庫、発注単位≧1、最小発注数量≧0、リードタイム≧0日。全項目未入力なら「補充設定なし」（提案しない）。

```
P = U + O
P ≦ 発注点 なら 必要数 = max(0, 目標 − P)
  必要数 > 0 なら 推奨 = ceil(max(必要数, 最小発注数量) ÷ 発注単位) × 発注単位
P > 発注点 なら 推奨 = 0
安全在庫割れ = U < 安全在庫（入荷予定があっても手元不足を隠さない）
```

- 保留は U に含めない。保留場所向けの発注残は O に含めない。
- 納期超過の発注残は自動で消さず、別警告として表示する。
- 希望納期の目安は今日＋リードタイム（暦日。休日は考慮しない）。
- 候補から下書き作成時に P を再計算し、表示時と違えば `BASIS_CHANGED`。下書き明細に作成時 P（`basis_p`）を保存し、発注済みにする直前にも再確認する（利用者が最新値を確認した場合のみ通す）。

## 8. 棚卸

- 1セッション＝1場所。開始時に場所行をロックして停止状態（`locations.stocktake_id`）と理論在庫・基準リビジョンを保存。以後、その場所に関係するすべての在庫書込みを `LOCATION_LOCKED` で拒否（移動は元・先どちらかが停止中なら全体拒否）。DBロックを保持し続けない。
- 状態：計数中 → 差異確認 → 確定、または中止。ブラウザ終了・時間経過では解除しない。
- 未計数は NULL。0 は明示入力。未計数が残ると差異確認に進めない。
- 差異＝実数−開始時理論。差異行は理由必須（「その他」はメモ必須）。差異0は在庫イベントを作らない。
- 棚卸行は version で競合検出。再計数は履歴を残し、差異確認済みを解除する。
- 確定：全差異イベント・残高・棚卸確定・停止解除・差異帳票スナップショットを1トランザクション。場所リビジョンが基準と違う、または残高が理論と違えば停止（古い理論で調整しない）。再確定は冪等キーと状態で二重調整しない。
- 中止：実数を反映せず停止解除。アプリ外で動かした事実を記録できる。
